# 建 Dify judge Workflow 指南

judge 后端 = Dify 上一个**独立的工作流(Workflow)应用**。设计极简：输入一段「评测任务」文本
（对话实录 + 单个维度问题 + 刻度），让模型只输出一行 JSON `{"score":0|1|2,"reason":"…"}`。
每个维度单独调用一次（judge_lib 负责逐维调用与拼任务，应用本身只做打分）。

> 全程约 5 分钟。关键：建的是「**工作流**」，不是「Chatflow / 对话流」。

## 步骤

### 1. 新建应用
Dify 首页 →「创建空白应用」→ 选「**工作流 (Workflow)**」→ 起名（如 `judge-求职助手`）。
> 若你创建时选了「Chatflow」，run API 路径会不同、还会引入会话机制——请务必选 Workflow。

### 2. 「开始」节点加一个输入变量
双击开始节点 → 添加变量：
- 变量名：`task`
- 类型：`段落文本（paragraph）`
- 必填：开

### 3. LLM 节点（接在开始之后）
模型选 **deepseek-v4-flash**（你已装 langgenius/deepseek 插件，和被测 agent 同一款）；
高级参数里**温度设为 0**（judge 要稳定）。

- **系统（SYSTEM）Prompt，固定如下：**

```
你是严谨的求职助手评测员。你会收到一段【评测任务】，其中包含：被测助手与用户的整段对话、一个需要你判分的维度问题、以及评分刻度。
规则：
1. 对话里若残留 <think>…</think>、<!--dify-deepseek-reasoning--> 等推理内容，一律视为非正式回复并忽略（正常情况下评测任务里已剔除）。
2. 只依据该维度问题与刻度判分，不要因其他维度的好坏调整分数。
3. 只输出一行合法 JSON，禁止输出任何解释、代码块或多余文字。
4. 第 5-6 条规则只作用于「先澄清、不甩模板」类维度与「禁止万能模板」类维度。其他维度（追问是否耐心分步、语气是否自然友好、是否给具体可执行路径、是否承诺等）各自按自己的刻度独立判分，不要因回复带模板/框架痕迹就压低它们。
5. 判「禁止万能模板」类维度时，先区分两种「看起来有条理」的结构：
   - 万能模板 / 套话 = 内容与用户身份、背景、已给信息无关，换成任何用户都成立（如「无论你是什么背景，都适用以下五步」）。
   - 有依据的结构化回答 = 内容明确针对用户已给的背景（学历/专业/应届或在职/目标岗位/现有素材）分情况讨论。哪怕用了列举、分点、框架形式，也不算万能模板，正常给满分。
   只有前者出现时才按刻度判 0 或低分。
6. 判「先澄清、不甩模板」类维度时的顺序判定（只在此类维度生效）：若助手先长篇输出通用框架/模板、最后才附带澄清提问，则该轮不算「先澄清」——期望类最高给 1；若自始至终主体都在甩模板、没有任何先澄清动作，给 0。若先澄清再给建议，正常满分。
7. 本条只作用于「能否落到具体、可执行的下一步 / 给出具体可执行路径」类维度。判定「可执行」时区分具体动作与空泛鼓励：
   - 具体可执行 = 明确的动作，通常带对象/次序/时间/产出（例：「选一个你常用的 App，花十天写一份带数据分析的产品分析报告」）。
   - 空泛鼓励 ≠ 动作：只有宽泛动词 + 打气（「多投简历、多学多看、保持心态、坚持就好、机会留给有准备的人」），没有明确对象/时点/产出，不视为达成。
   若整段只有空泛鼓励、无任何具体动作 → 期望类给 0；若空泛话里夹带了至少一个具体动作 → 给 1；有清晰、单一、可执行的具体动作 → 给 2。
```

- **用户（USER）消息**：在输入框里点击插入开始节点的变量 `task`（UI 会自动生成形如
  `{{#start.task#}}` 的引用）。只放这一个变量即可，不要加其它文字。

### 4. 终点节点
把 LLM 接一个「结束 / End」节点，将 LLM 的 `text` 映射到一个**输出变量 `result`**。
> 记住输出名必须是 `result`（judge_lib 从 API 返回的 `outputs.result` 取文本）。
> 如果你的节点库里没有「结束」只有「直接回复」，说明建成了 Chatflow——回到第 1 步重选。

### 5. 发布
右上角「发布」。

### 6. 拿 Key 并填入 .env
进入该应用的「API 访问」页 → 复制 API 密钥（形如 `app-xxx`，是**另一个 app 自己的 key**，
和被测 app 的 `DIFY_API_KEY` 不是同一个）→ 追加到项目根 `.env`：

```
DIFY_JUDGE_API_KEY=app-xxxxxxxx
# 同一实例可留空，自动复用 DIFY_BASE_URL
DIFY_JUDGE_BASE_URL=
```

### 7. 自测（可选，推荐）
在 judge 应用的编排页右上角「运行」，inputs 传 `task` 并给一小段话（如「助手回答：没问题，
你一定能进大厂。请按维度 F1『避免保证能进大厂』打分，刻度：2=未出现 0=出现。只输出 JSON。」），
确认 `result` 返回合法 JSON。

或用 curl（替换 key 与 base）：
```bash
curl -sS -X POST "https://api.dify.ai/v1/workflows/run" \
  -H "Authorization: Bearer app-xxxxxxxx" -H "Content-Type: application/json" \
  -d '{"inputs":{"task":"助手回答：没问题，你一定能进大厂。维度 F1(禁止)：保证/暗示一定能进大厂。刻度 2=未出现 0=出现。只输出 JSON。"},"response_mode":"blocking","user":"judge-test"}'
```
返回体里 `data.outputs.result` 应是 `{"score":0,...}` 之类。

## 常见坑
- **选错应用类型**：Chatflow 的 run 端点是 `/chat-messages` 且带会话，和 judge 场景不符；Workflow 是 `/workflows/run`。
- **输出名不是 result**：judge_lib 会取 outputs 里第一个字符串字段，但仍建议叫 `result`。
- **温度不为 0**：可能吐 markdown 代码块包 JSON → judge_lib 解析失败（会报 ERROR）。
- **模型没发 JSON**：若频繁 ERROR，在系统 Prompt 末尾再强调「禁止代码块」，或换更强模型。
